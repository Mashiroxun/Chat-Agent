把洛版 0.4.9.1 换到 0.5 的模块化底座

结论先说：能实现，但"改造底层"这个说法会把人带进坑里。 这不是给旧房子换地基——是搬进新房子，家具能带走，承重墙带不走。 真正的问题是：洛版那 5,261 行的分层记忆，在新房子里有没有位置。

证据来源 两侧源码逐文件比对 关键发现 0.5 已内置 migrateFrom04 硬障碍 2 处（内核接口 / 分层记忆）
可行，但要选对路线：迁移，不要重构

① 官方 0.5.0 里已经有 src/kernel/migrator.js，导出 detectMigrationSource / migrateFrom04——0.4 数据迁移是设计内的功能，不是你要自己造。覆盖 config / messages / memory / stickers / reminders / telemetry 六类。

② 洛版 13 个插件里 9 个只用了 api.config + api.log + api.storage + registerTool，0.5.0 的 compat-04 垫片正好覆盖这几个——接近零改动就能跑。

③ 但内核三件套（编排器 / 记忆仓 / 发送队列）接口签名完全不同，洛版模块塞不进 0.5 的组件位。这两层必须二选一：用 0.5 的，或者写适配器。

01为什么"改造 0.4.9.1 的底层"这条路不成立

如果你说的是"把洛版现有代码原地重构成模块化"，那等于重写——原因不是代码量，是耦合方式。

0.5.0 的"模块化"不是把文件拆小，是三件套：依赖注入 + 组件表 + 生命周期登记。而洛版代码里全是直接 import 和 this.xxx 调用：

// 洛版 src/app.js —— 41 个顶层 import，全部直接绑定具体实现
import { Orchestrator } from './orchestrator.js'
import { MemoryStore } from './memory.js'
import { SendQueue } from './sender.js'
import { ChatStore } from './store.js'
// ... 共 41 行 import，没有一个是通过参数传入的

// 0.5.0 src/kernel/orchestrator.js —— 实现从组件表取，可被 overrides 替换
const systemPromptFor = components?.['core.prompt.system'] ?? buildSystemPrompt;
const userPromptFor   = components?.['core.prompt.user']   ?? buildUserPrompt;
const agentRunner     = components?.['core.agentRunner']   ?? runAgent;

要把洛版重构成这个形态，得把 orchestrator.js（3,700 行）、routes.js（5,286 行）、app.js（3,977 行）逐段拆开、把每处 this.store.xxx() 改成注入、再补上 lifecycle.onStop 的清理登记。工作量约等于重写一遍 0.5，而且拿不到 0.5 的任何测试与文档红利。

所以问题应该重新表述

不是"怎么把 0.4.9.1 改造成模块化"，而是"怎么把洛版的能力搬到 0.5 的模块化底座上"。前者是重写，后者是迁移——后者可行，下面全是后者。

02三条路线的真实成本

推荐

A · 迁移到 0.5

洛版功能以追加层/插件形式挂上 0.5，内核用 0.5 的
  • 数据靠官方 migrator 六类导入
  • 9 个插件走 compat-04 直接跑
  • 桌宠壁纸已有现成参考层
  • 内核语义接受 0.5 版本
代价：内核行为要重新验收，不是原样保留

B · 原地重构 0.4.9.1

保持 0.4 内核，只把代码组织改成模块化
  • 视觉上像 0.5，内核还是 0.4
  • 要拆 13,000 行巨型文件
  • 拿不到 0.5 的组合/覆盖能力
  • 拆完仍需自己维护两套
代价：纯投入，无架构收益 —— 不推荐

C · 双轨并存

0.4 继续日常用，0.5 侧逐步接管特定能力
  • 这个 portable 包已在做（洛希桥）
  • /dsh 命令切换主脑
  • 风险隔离最好
  • 但两套数据两套配置
代价：长期双份维护，适合过渡期

下面按 路线 A 展开，因为它是唯一能同时拿到"洛版能力"和"模块化架构"的路径。

03好消息：这三块几乎不用你动手

3.1 数据迁移 —— 官方已经写好了

src/kernel/migrator.js（238 行）的设计约束很明确：0.4 目录只读、永不回写、目标 data 必须为空、支持 dryRun，迁完写 migration-report.json。它处理六类：

类别迁移内容洛版实测状态
① configconfig.json，剥离废弃键与 derived flags47 KB可迁
② messagesmessages/ 整目录11 MB可迁
③ memorymemory/，含 0.4 旧单文件格式自动拆分383 KB可迁
④ stickersstickers.json + sticker-images/103 KB可迁
⑤ reminders提醒任务—可迁
⑥ telemetry沿用 installId78 B可迁
但注意：迁移器只认官方 0.4 的六类

洛版 data/ 下这些不在迁移范围内，需要你自己决定：memory-v3/（5.5 MB，mem-layered 的私有数据）、usage-ledger/、usage-daily.json、plugin-data/、desktop-pet/、sessions/（8.1 MB）、image-cache/、video-cache/、cache-warm-prefix.json、bridge/。其中 memory-v3 是最大的问题，见第 4 节。

3.2 九个插件 —— 兼容垫片直接吃

统计洛版 13 个插件的实际 API 调用面，结果出乎意料地窄：

而 bundled/compat-04/index.js 提供的兼容面正好是 config / log / warn / error / capability / hasCapability / registerTool / utils，并且明确保留"未标记用户包可调用旧配置入口"和"旧 parameters / execute(ctx,args) 自动映射到新顺序"。

3.3 桌宠和壁纸 —— 已经有人替你搬过了

这个 portable 包里的 overrides/30-desktop-extras/ 就是活样板：它把洛版的桌宠 + 壁纸整体接到 0.5 上，用了 wrap console.panels 插两页 + 独立路由 /api/pet/*、/api/wallpaper/* + 独立 Electron 进程，没改 0.5 的任何出厂文件。README 里连"模糊的根因是小红车预览图只有 1024px"这种细节都写了。

要搬洛版其他重 UI 功能，照这个结构抄就行。

04坏消息：两块硬骨头

4.1 内核三件套接口不兼容（这是根本性障碍）

如果你打算"把洛版的编排器/记忆仓/发送队列直接塞进 0.5 的组件位"，先看这张表：

模块洛版 0.4.9.10.5.0兼容
编排器 new Orchestrator({store, memory, sender, sessions, onebot, emit, reminders, videoReader})
8 个依赖，对象字面量		 createOrchestrator({cfg, store, sessions, memory, send, registry, loader, capability, transport, onebot, log, bus, isPaused, buildToolsFor, execContextFor, transcribe, now, llmInvoker, components, lifecycle, ...})
20+ 依赖，内部再按组件表取提示词/运行器		 不兼容
记忆仓 18 个公开方法：append / query / remove / editMemberImpression / formatForPrompt / mergeMemberInto / listChats / markConsolidated / … 公开面只有 mergeNameDuplicates / migrateLegacy / persist，其余在闭包里 公开面不同
发送队列 sendTextBatch / sendImage / sendMedia / sendSticker sendTextBatch / sendImage / sendSticker / sendSegments / poke 部分重叠 sendMedia 无对应
这意味着什么

洛版的 Orchestrator 不能被塞进 0.5 的 core.orchestrator 组件位——除非写一个适配器，把 0.5 传进来的 20 个依赖映射成洛版要的 8 个，并且再把洛版内部对 this.store.xxx() / this.memory.xxx() 的调用翻译成 0.5 的接口。这个适配器本身就是个几千行的兼容层，比直接用 0.5 的编排器再补功能更贵。

正确做法：内核用 0.5 的，洛版的增强做成插件挂在外面。

4.2 分层记忆 mem-layered：5,261 行，最麻烦的一块

这是洛版最有价值的差异化功能（BM25 检索 + Weibull 衰减 + 共激活联想 + 后台增量巩固），也是迁移里唯一的"重资产"：

维度洛版 mem-layered0.5.0 memory-service
代码量5,261 行（20 个文件）约 300 行
数据位置data/memory-v3/（blocks / index / cards / cross-turn / todos / budget / stats）
实测 5.5 MB		data/memory/（按 QQ 号一人一文件，每条印象截断 300 字）
检索BM25 索引 + 强度衰减 + 联想激活最近 15 成员 × 每人 3 条印象，直接塞提示词
迁移器覆盖不覆盖迁移器只迁官方 memory/ 格式

三个选择，代价递增：

  • 方案 1（最省）：把 mem-layered 当插件整体搬过去，数据目录继续用 memory-v3。它只用 api.config + api.log + registerTool + api.capability，改一处能力位注册即可。5.5 MB 历史记忆原样保留。推荐这条。
  • 方案 2：写一次性转换脚本，把 memory-v3/blocks/ 里的日块摘要导出成 0.5 的 memory/*.json。结构差异大（块是"按天的对话摘要"，0.5 是"按人的印象条目"），信息损失严重，BM25 索引和衰减曲线全丢。
  • 方案 3：放弃洛版记忆，用 0.5 原生的。最干净，但洛版最核心的能力就没了——那迁移的意义少一半。

4.3 sticker 插件：qqCall 在 0.5 里不存在

洛版 sticker 插件用 api.qqCall('fetch_custom_face_detail') 直接调 OneBot 拉 QQ 收藏表情详情。全量 grep 0.5.0 源码，qqCall 零命中——0.5 不给插件直连 OneBot 的口子（这是安全设计，文档写明"桥只监听回环，插件拿不到 OneBot"）。

0.5 的替代是 execution.send.sendSticker(chatKey, sticker, options)，只管发不管拉。所以要保留"同步 QQ 收藏表情"这个功能，得走 bundled/transport-onebot 暴露的能力位，或者干脆砍掉这一支、只保留本地表情库。

4.4 测试不可复跑，回归全靠自己

0.5.0 的 test/ 目录没随包分发（package.json 有 test/run-all.mjs 但目录缺失）。洛版那 31 个测试文件、235 条用例，测的是 0.4 的接口。迁移完成后没有现成的回归网，得自己重建。

05执行路径（按可验证的里程碑切）

每一步都能独立验收，不要一次性全搬。前两步是"证明可行"，不是"完成迁移"。

先跑通数据迁移，确认能启动

不写一行新代码，先验证官方迁移器能不能吃下洛版的 data。这一步失败，后面都不用谈。

在 0.5 的空 data 目录旁放一份洛版 data/ 副本，调 detectMigrationSource 看它认不认；再 migrateFrom04({dryRun:true}) 出报告，核对六类条数与洛版实际是否对得上。

验收：migration-report.json 六类全 ok，config 的 47 KB 关键字段（providers / 白名单 / 人设）在 0.5 设置页可见

搬第一个"零风险"插件：cache-guard

269 行，纯观测型、不改任何行为，只用 api.config + api.log + registerTool。用它验证 compat-04 垫片到底能不能接住洛版插件。

整个目录丢进 plugins/，看加载器是否识别、工具是否注册、日志是否出现"旧接口被调用"的兼容记录。

验收：面板里能看到缓存命中率报表，且 compat-04 的 compatibility 字段记录了旧接口调用

批量过 7 个小插件

ban-state / image-compat / owner-identity / speaker-identity / speech-to-text / video-frames / account-pool / thinking-adapters —— 依赖面都一样窄。

逐个搬、逐个启，遇到 api.capability 的改成 ctx.capability 显式注册；遇到 api.thinkingMode 的对照 src/kernel/thinking-policy.js 的字段名改。

验收：每个插件在设置页有配置项、能力位注册成功、日志无报错

攻坚 mem-layered

最大价值也最大风险。策略是"当插件搬，不碰内核"——让它继续管自己的 memory-v3。

改 api.capability → ctx.capability；确认它能拿到 data 根路径；把 5.5 MB memory-v3 整目录拷进新 data 根。不要试图把它的记忆导进 0.5 的 memory/。

验收：拿一个真实群的历史提问，能检索出 10-22 的旧记忆块，且衰减强度值与洛版一致

补 UI：把洛版专属页接回来

洛版的记忆页、用量页、桌宠页在 0.5 里要么没有、要么语义不同。

照 overrides/30-desktop-extras/ 的结构写新的追加层：composition.json 声明 ui.panels，assetRoot 指向你的页面，api 白名单只放需要的接口。

验收：侧边栏出现新页，删掉该层目录重启后完全恢复出厂

重建回归网

0.5 的测试没随包，迁移后没有任何安全网。

优先补洛版 CHANGELOG 里踩过的坑：图片压缩分支、244 万字符请求体、被禁言不烧 token、插件指纹校验。这些是实战验证过的回归点。

验收：至少覆盖"发图 / 长上下文 / 禁言 / 插件重载"四条主链路

06必须提前接受的四个事实

① 迁移后不是"洛版 0.4.9.1"，是"洛版功能 + 0.5 内核"

内核语义会变。洛版那些靠改内核实现的行为（响应档位判定、忙时合批、上下文锚点、峰谷计价），0.5 有自己的实现，细节不一定一致。0.5 的 core-behavior-parity.md 自己就写了"旧活跃 TTL 把 60000 当分钟下限的实现不迁入"——官方是主动选择不兼容某些旧行为的。

② 洛版 298 KB 的实战修复，大部分带不过去

那些修复散落在 orchestrator.js、routes.js、app.js 内部，不在插件层。迁移只能带走插件和 UI，带不走内核里那几百条边角修复。这是"0.5 更干净但更嫩"的代价。

③ 追加层的信任等级 = 改源码

overrides/ 不受市场安装器管控、不走插件权限模型。它换来"什么都能换"，代价是"什么都能坏"，且必须完整重启才生效。别把不可信的第三方代码往这里放。

④ 双轨过渡是合理的，不必一次切换

这个 portable 包里的 50-luoxi-bridge 已经示范了过渡形态：0.4 和 0.5 并存，用 /dsh <任务> 把特定会话交给另一侧，core.ingest 返回 accepted:false 让宿主整链跳过——同一时刻只有一个主脑。迁移期间可以两边跑，一条群用旧的、一条群试新的。

07一句话回答

能，但要把问题从"改造底层"改成"迁移能力"

数据有官方迁移器（六类），九个插件有官方兼容垫片（compat-04），桌宠壁纸有现成样板（30-desktop-extras）——这三块占了洛版功能面的大半，且几乎不用自己写。

真正的成本在两处：mem-layered 只能当插件整体搬、不能融进 0.5 的记忆仓；内核语义要重新验收、洛版几百条边角修复带不过去。

如果目标是"长期可维护的洛版"，值得做；如果目标是"原样保留 0.4.9.1 的所有行为细节"，那不该迁移——继续在 0.4.9.1 上迭代更划算。
