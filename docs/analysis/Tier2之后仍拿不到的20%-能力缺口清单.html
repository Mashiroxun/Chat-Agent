Correction · Gap Inventory

剩下那 20%，具体是哪些东西

先纠正一个口径问题：我说的"80%"指的是实用价值，不是覆盖率。 按组件数算，Tier 2 之后洛版能替换的是 6 / 60 ≈ 10%。 下面把这 90% 摊开——它们不是"搬不动的功能"，而是"让搬过来的东西真正生效的机制"。

先修正上一份里一个过于乐观的判断

我说过"第 6 步拿 30-desktop-extras 验收，跑起来就说明对齐了"。核实后：它跑不起来。

它依赖三个组件——console.panels（wrap）、core.tools.bundle（wrap）、ui.panel（页面声明）——洛版一个都没有。它唯一能对上的只有 core.send 的 wrap 和 routes 注册。

所以 Tier 2 的验收标准要改：不能拿现成的 0.5 层来验，只能自己写一个"只依赖那 6 个组件"的最小测试层。

01三个尺度的 80 / 20

80%
实用价值
日常最想改的：数据格式、发送行为、编排流程。这 6 个组件恰好覆盖
10%
组件覆盖率
0.5 组件表 60 项，洛版能替换 6 项（data.*×4 + core.send + core.orchestrator）
≈0
生态兼容度
0.5 的追加层几乎全都依赖 console.panels / ui.panel / 细粒度 core.*

这三个数字不矛盾，但必须分清：Tier 2 拿到的是"可替换这个机制"，不是"能跑 0.5 的扩展生态"。前者对你的项目有价值，后者基本为零。

02六类拿不到的东西

按"缺了会怎样"排序，不是按重要性。

1

页面注册机制

console.panels + ui.panels

0.5 的页面是数据驱动的：ui.panels 声明 {id, title, entry, assetRoot, permissions, api}，宿主据此渲染侧边栏、挂静态资源、校验 API 白名单。加一页 = 加一个目录 + 一段 JSON。

洛版的侧边栏是 ui/index.html 里硬编码的 #tabs .nav-item（39 KB 静态 HTML），页面切换靠 14-chrome.js 遍历 DOM。

后果：加页要改 HTML + 加脚本，换页要改 3,700 行的 06-settings-render.js。0.5 那种"整页替换、删目录即恢复"做不到。
2

细粒度策略组件

23 个 core.* / llm.*

0.5 把业务策略拆成了 23 个独立函数：core.prompt.system / .user / .pastState / .anchor / .persona、core.wake.resolve、core.memory.consolidate、core.text.plain / .split、core.tools.bundle / .parseInline、core.reply.rescue、core.events、core.session.retryable、core.media.forward、core.agentRunner、core.ingest、llm.complete / .target / .thinking。

洛版这些全在 orchestrator.js（3,700 行）和 app.js（3,977 行）内部，以私有方法形式存在，没有任何导出。

后果：最常想改的东西全都改不了。想换系统提示词构造、想改唤醒档位判定、想给工具束加一层、想拦截模型调用——只能改源码，没法加覆盖层。
3

wrap 模式（只能换，不能包）

语义缺失

0.5 的 mode: "wrap" 导出 (previousFactory, {key, ownerId}) => nextFactory，可以只增强某个方法、保留其余全部行为。洛版那 8 个是 new Xxx() 出来的类实例，工厂表只能"整体换掉构造器"。

后果：想"给 SendQueue.sendTextBatch 加个日志"这种小改动，要么写子类覆盖、要么改源码。0.5 里这是一层 10 行 JSON + 5 行 JS 的事。
4

运行时基础设施

13 个 runtime.*

runtime.capability / permissions / tools / scheduler / storage / plugins / http / sdk / services / serviceLease / fetch / priceUpdates / instanceLock。

洛版有对应的文件（skills/capabilities.js、tool-guard.js、tool-registry.js、safe-fetch.js、instance-lock.js…），但没集中成表，而且互相直接 import。

后果：想换 HTTP 安全层、想换调度器、想换权限引擎——要改的是多处调用点，不是一处查表。这层"能换"的价值远大于表面数字。
5

治理机制

不是组件，是机制

权限门（net.outbound / proc.exec 声明与授权）、能力代际（提供者切换后旧事件不得写入、旧代结果不得进新代）、服务租约（serviceLease）、数据重置协调器（runtime.reset.complete / runtime.reset）。

洛版有 checkPluginTrust 的指纹校验和 tool-guard.js，是另一套语义（按文件 sha1 认模块，不按能力授权）。

后果：即使给洛版装上 overrides 层，层里写的权限声明是装饰性的——没有东西去执行它。0.5 的"层不能偷偷拿 OneBot 和 console token"这条保证，在洛版上不成立。
6

诊断与归属查询

2 个工具

0.5 有 scripts/inspect-composition.mjs（不启动就静态预检：显示实际选择、完整来源链、冲突决议、同优先级提示）+ GET /api/composition（运行时查询"这个行为到底是谁提供的"）。

洛版两者都没有。

后果：层叠冲突只能靠启动报错发现；出问题时无法回答"是出厂实现还是我的覆盖层在起作用"。层数一多，这个能力比什么都重要。

这 6 个恰好是数据层全部 + 主链路两端。日常真正想改的东西——消息怎么存、发出去长什么样、一轮对话怎么编排——都在这 6 个里面。

所以"80% 实用价值"这个说法成立，但只在"你自己维护自己用"的前提下成立。一旦你想用 0.5 的扩展生态，这个数字立刻变成 0。

04如果要把那 20% 也补上

两个机制，代价差一个数量级。

机制要改什么代价值不值
console.panels
页面顺序 / 注册 / 追加		 把 ui/index.html 里硬编码的 #tabs .nav-item 改成从数组渲染；14-chrome.js 改动态生成；app.js 暴露 /api/panels 约 300–500 行 值。做完就能"加页不改源码"
ui.panels
整页替换 / iframe 隔离		 洛版是单页 SPA，要做整页替换得引入 iframe 沙箱 + token 校验 + assetRoot 静态服务 + API 白名单 约 800–1500 行 不太值。会破坏现有页面样式一致性，且 20 个全局脚本共享作用域，隔离做不干净
细粒度 core.*
23 个策略函数		 把 orchestrator.js 里的私有方法逐个提取成可导出函数，再接到工厂表 等于重写编排器 这就是 Tier 3 第 7 步。做完洛版就不是洛版了
一个折中：只补 console.panels，不补 ui.panels

300–500 行能拿到"加页自由"——侧边栏想加多少页都行，每页可以是独立 HTML + 独立 JS，走自己的路由。这覆盖了 0.5 追加层 80% 的实际用途（像 30-desktop-extras 那样加桌宠页、壁纸页）。

换页（ui.panels 替换已有页面）放弃——洛版 UI 那个共享全局作用域的结构，硬做隔离得不偿失。想换页就直接改源码，反正只有你自己维护。

05一句话总结

那 20% 不是"功能"，是"粒度"

Tier 2 给你的是8 个粗粒度替换点。0.5 给的是 60 个细粒度替换点 + 一整套治理机制。

差的那 90% 组件里，真正影响日常的是细粒度策略（23 个）和页面注册（2 个）；剩下的是基础设施和治理——那些东西你平时不会想换，但出事时它们决定你能不能定位问题。

所以务实的选择是：Tier 2 + 补 console.panels。约 400 行，拿到"数据/发送/编排可替换 + 页面可自由添加"，覆盖你自己维护自己用这个场景的绝大部分需求。剩下的别补了——补它的代价是把洛版重写成 0.5，那就绕回原点了。

核实来源：bundled/runtime-defaults/components.js（defaultComponents 共 60 项，逐项提取）、 overrides/30-desktop-extras/composition.json（依赖 console.panels / core.tools.bundle / core.send / ui.panel）、 ui/index.html（39,952 字节，#tabs .nav-item 硬编码）、ui/app/14-chrome.js:1306（DOM 遍历切换页面）。 上一份《硬改方案》第 6 步的验收标准已按本节修正。
