01为什么不建议继续开放组件

实测的调用点数量，决定了改造成本。

全局依赖引用文件调用次数做成组件的成本
getConfig / updateConfig24317要改上千处
skillManager15232要改上千处
logger21186要改上千处
DATA_DIR26116要改上千处
safeFetch216可做

这些不是"耦合不好"，而是它们本来就是单例语义——配置、日志、插件管理器、数据根目录，整个进程只有一份。硬做成可替换，等于给每个调用点加一层间接，换来一个你几乎不会去替换的能力。

判断标准很简单：你会不会真的去换它？
提示词、上下文选取、模型调用——会换，所以 0.4.9.2 做了。
日志实现、配置读取、插件加载器——不会换，所以别做。

02机会一：拆 routes.js（性价比最高）

1

5,286 行 / 177 条路由，按域拆成 15 个文件

低风险高收益

关键发现：createRoutes(deps) 返回的是一个纯数据数组，不是 if-else 链：

// src/routes.js 末尾
return [
  { method: 'POST', pattern: '/api/wallpaper/import', handler: async ({ req, res, url, json }) => { ... } },
  // ... 共 177 条
];

这意味着拆分只是把数组元素搬到别的文件，没有任何控制流改动：

// src/routes/forge.js
export const forgeRoutes = [ /* 15 条 */ ];

// src/routes/index.js
import { forgeRoutes } from './forge.js';
import { fixRoutes }   from './fix.js';
export function createRoutes(deps) {
  const ctx = makeRouteContext(deps);   // json / bodyOf / sse 等共用工具
  return [ ...forgeRoutes(ctx), ...fixRoutes(ctx), /* ... */ ];
}

按域的实际条目数：

域条目域条目域条目
/api/forge15/api/providers12/api/bundle8
/api/fix15/api/protocol12/api/market7
/api/dev12/api/doctor10/api/skills6
顺带拿到的好处：拆完之后，console.routes 就成了天然的可替换点——覆盖层可以追加自己的路由表，或者替换某一个域（比如把 /api/providers 整套换掉）。这是 0.5 里 console.routes 的做法，洛版现在做不了。

03机会二：把 app.js 里的功能块外提

2

qq-portable 一整套（约 300 行）跟主流程无关

低风险中收益

createApp 里有 53 个内部函数，其中这一组是完整独立的子系统：

函数行数作用
qqPortableDir / qqPortableDataDir / qqPortableExe12路径推导
qqPortableReady42就绪探测
listQqProcesses / __listQqProcessesOnce / qqPortableRunningPid49+进程枚举
launchPortableQQ / stopPortableQQ / qqPortableStatus约 150启停与状态
pushQqLog / isPortOpen52日志与端口

它们只依赖 log 和几个路径常量，不碰 store / memory / orchestrator。抽成 src/qq-portable.js 之后，createApp 少 300 行，而且这套进程管理能被单独测试（现在一个测试都没有）。

同类候选：chatApi（76 行，桌宠私聊）、getUsageToday（25 行）、devApi（20 行）。加起来还能再瘦 120 行。
不要动：handleOneBotEvent——它跟协议端、SSE、桌宠事件转发缠在一起，是真正的中枢。

04机会三：结构性收尾

3

20 个 .bak 文件 —— 这是最大的技术债

零风险但最重要

routes.js 有 4 个备份、03-connection.js 有 3 个、style.css 有 3 个……这说明每次改动前的"保险"是手工复制文件。

实测差异：routes.js.bak-20261028-fixstatus 与当前只差 24 行，.bak-20261027-adaptprogress 差 379 行——这些都是历史快照，没有未合入的改动，可以安全清理。

但比清理更重要的是：初始化 git 仓库。

cd G:\QQagent\resources\app
git init
printf 'node_modules/\ndata/\n*.bak*\n' > .gitignore
git add -A && git commit -m "0.4.9.2 启动组合改造基线"
有了 git，以后每次改造都是一个 commit，出问题 git checkout 就回来——再也不用 .bak。而且 0.4.9.2 引入的 overrides/ 让实验性改动可以直接放层里，连源码都不用碰。这两件事配起来，才是"可持续维护"。
4

补一个诊断接口：查"这个行为是谁提供的"

纯新增中收益

现在有 scripts/check-composition.mjs 做启动前预检，但没有运行时的归属查询。层一多就会问："这条提示词是出厂实现还是我的层在起作用？"

加一个 GET /api/composition，返回当前进程实际绑定的组件来源（不返回模块路径、不返回函数体）：

{
  "layers": [{ "id": "example", "order": 10, "components": ["core.prompt.system"] }],
  "components": {
    "core.prompt.system": { "owner": "example", "shadowed": ["defaults"] }
  }
}
约 60 行，纯新增，不影响任何现有路由。对应 0.5 里 GET /api/composition 的角色。
5

测试覆盖补缺：68 个模块只有 31 个测试文件

持续投入长期收益

已有测试集中在：消息规范化、发送守卫、缓存归因、禁言复核、协议启动、桌宠窗口、表情库、壁纸模块——都是踩过坑的地方，这个分布其实很合理。

缺口在本轮改造涉及但没测的：src/composition/loader.js（清单校验、路径穿越拦截）、factories.js（键名校验）。这两个是新增代码，建议补 tests/composition-loader.test.mjs——约 8 个用例，覆盖：非法版本 / 重复 id / 路径穿越 / 符号链接 / 非函数导出 / enabled:false / order 排序 / 覆盖优先级。

新增代码没有测试，等于把风险留给下次改动。这是本轮改造唯一的"未收尾"。

06如果只做一件事

上 git

不是因为代码问题，是因为你现在的改动方式没有退路。20 个 .bak 文件就是证据——每次动 routes.js 之前先复制一份，改坏了再拷回来。

有了 git 之后：routes.js 那 5,286 行拆不拆、拆错了怎么办，都不再是风险问题，只是 git checkout 的成本。所有重构的前提，都是先有一个能退回去的地方。

而 0.4.9.2 的 overrides/ 已经把"实验性改动"这条路铺好了——想试什么新规则、新提示词、新发送策略，写个层丢进去，删目录就恢复。这两件事配起来，你才真正不用再留 .bak。

实测来源：src/routes.js（177 个 pattern: 条目，返回纯数组）、src/app.js（53 个内部函数，qq-portable 组约 300 行）、 src/cache-warm.js（SHAPE_MAP_MAX / earlyWarmDone.size > 64 已有淘汰）、 全局依赖引用数为 grep -rl / grep -rho 实测、.bak 差异为 diff | grep -c 实测。
