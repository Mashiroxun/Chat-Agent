Architecture Audit · 2026-11-03

QQ Agent 0.5.0 vs 洛版 0.4.9.1

0.5.0 不是"在 0.4 上继续加功能"，而是换掉地基重写。它的 package.json 自己写着： "DSH 薄内核 + 全插件架构（行为等价 0.4，实现从零）"。所以两者的差距不在功能条数， 而在代码被切开的方式——以及切开之后，洛版那些独有能力还剩多少。

对照样本 qq-agent-0.5.0-portable (546 MB) 基线 洛版 v0.4.9.1（G:\QQagent） 方法 解包逐文件比对 + 文档/清单核验

01一句话结论

0.5.0 赢在架构与可维护性，洛版赢在功能密度与实战打磨

0.5.0 把 12 万行摊平的单体拆成了 7 个领域目录 + 20 个可插拔内置模块，最大单文件从 5,286 行降到 1,501 行，并提供了 0.4 完全没有的东西：不修改出厂文件的追加式覆盖层。

洛版 0.4.9.1 的 13 个增强插件里有 6 个（含 5,261 行的分层记忆、1,565 行的 B站/抖音下载）在 0.5.0 里没有等价物；它的 8 个技能里也只剩 2 个能对上。

换句话说：0.5.0 是更好的底座，0.4.9.1 是更完整的成品。而 0.5.0 真正的杀手锏，是这个 portable 包里已经演示过的那件事——把洛版功能"挂"回去，一行宿主代码都不用改。

03架构：从"摊平的 src"到"可替换的组件表"

这是 0.5.0 唯一真正不可替代的优势，也是"模块化改造"这个说法的落点。

3.1 追加层到底是什么

0.5.0 在启动时扫描 APP_ROOT/overrides/<层目录>/composition.json，按 order 升序叠加，对每个目标组件做两种操作之一：

  • replace：整块换掉某个实现（如"系统提示词构造器"、"整个会话页"）
  • wrap：(previousFactory) => nextFactory，包一层再交回去，可以只增强某个方法

关键语义是逐目标裁决：A 层提供 X、Y，B 层提供 X、Z，冲突只发生在 X，Y 和 Z 各归各家，不会出现"整层被判输家"的连带停用。层内还有 requires 强依赖、64 层上限、路径穿越/符号链接拦截、inspect-composition.mjs 静态预检。删掉目录或 enabled:false，下次完整启动即恢复出厂。

代价也要说清：启动组合是原生代码，信任等级等同于直接改源码，文档自己写了"Node 插件和启动模块均不能被描述为原生代码沙箱"。

反过来：0.5.0 有、洛版没有的

  • 组合式覆盖层（overrides + replace/wrap + 逐目标裁决 + 静态预检）—— 0.4 无此概念
  • MCP 桥接（bundled/mcp-bridge，受权限管控的 stdio 客户端）
  • 签名自动更新（src/update 五个模块 + update-public-key.pem + 健康检查）
  • 多账号体系（src/accounts：manager / worker / gateway / appearance，独立进程隔离）
  • 协议管理域（src/protocols：登录、验证连接、进程树回收、初始密码）
  • 管理原语（src/management：节点/端口/作用域/序号/规则，14 个模块）
  • 扩展开发工具链 + AI 引导提示词 + 在线更新
  • 80+ 篇接口契约文档（含 extension-reference.md 48 KB、plugin-sdk.md 27 KB）

05这个 portable 包的真实构成（重要）

它不是"纯官方 0.5.0"

解包后 overrides/ 下已经有 三个自定义追加层，README 明确写着"移植自 0.4.9.1"、"没有修改 0.5 的任何出厂文件"。这既是最好的模块化证明，也意味着你拿到的不是干净基线。

06该警惕的地方

① 测试没随包

package.json 里 "test": "node test/run-all.mjs"，但解包后 没有 test/ 目录（build.files 也没包含它）。质量证据全在 docs/headed-qa-results.md（275 KB）等文档里——是"我测过"的自述，不是可复跑的用例。洛版则随包带 31 个测试文件。

② "行为等价 0.4" 是目标，不是已验证结论

docs/v04-extension-parity.md 自己用了大量"等价是源码合同判断，不是全部真实 QQ/外部服务验收已通过"、"实测另记"、"文档不能补出运行时能力"这类措辞，并把 available() 动态自检等列为缺口。加上洛版 0.4.9.1 那 298 KB CHANGELOG 里成百上千条实战修复（例如 ffprobe 缺失导致压缩分支从未执行、244 万字符请求体），0.5.0 大概率还没踩过这些坑。

③ 组合层的信任等级 = 改源码

overrides/ 不受市场安装器管控、不走插件权限模型。它换来的是"什么都能换"，代价是"什么都能坏"，且必须完整重启才生效（启动时绑定）。

④ 插件生态迁移有硬坑

0.4 插件最常写的 execute(ctx, args) 在 0.5 native 里变成了 handler(args, execution)——参数顺序反转。没标兼容标记的用户包会被 compat-04 垫片自动适配，但显式声明 params 的包必须自己改。洛版那 13 个插件若要在 0.5 上跑，逐个都要过一遍。

07如果要把洛版能力搬上 0.5.0

按"移植成本 / 收益"排个序，前三个值得先做：

优先级目标落点难度
P0mem-layered 分层记忆（5,261 行，洛版最核心的差异化）bundled/memory-service 用 replace 整块替换；数据在 data/memory-v3，需要迁移器高（含数据结构迁移）
P0cache-guard 前缀缓存归因（269 行，纯观测、零风险）wrap llm.complete 统计命中率 + 指纹化系统提示，报表挂 console.routes低（最佳练手对象）
P1media-download（1,565 行）新 bundled 模块，钩 core.ingest 的媒体链接中
P1speaker-identity / image-compat / account-pool三个小插件，compat-04 大概率直接吃得下低
P2help-board / keyword-reply / random-image 等 6 个技能按新 SDK 重写，参考 examples/extensions/中（数量多）

做完 P0 两项，0.5.0 才算真正"追平并超过"洛版 0.4.9.1；在此之前，日常用还是洛版稳，折腾架构选 0.5.0。
