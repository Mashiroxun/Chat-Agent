硬改方案：把 0.5 的装配方式搬进 0.4.9.1

既然要改，那就不劝了。但先给三个意外的好消息——它们让"硬改"从"重写一遍"变成 "改 27 行 + 加 1 个文件"就能拿到 80% 的收益。下面是分四档的施工方案，每档都能独立停下。

切口 src/app.js:968–994 新增 1 个容器文件 首档风险 极低（行为零变化）
能改，而且不用先动业务代码

洛版的装配点只有 8 个 new，连续 27 行，集中在一处（src/app.js:968–994）。这不是"几千处硬编码耦合"，是"一个装配块"。

把这块改成从工厂表取，就立刻拥有了 0.5 的核心能力——不修改源码即可替换任意组件。业务逻辑一行不动，洛版那 298 KB CHANGELOG 里的实战修复全部保留。

之后要不要继续把实现逐个换成 0.5 的，是独立决策，不是必选项。

// src/composition/factories.js —— 新增文件，约 60 行
import { ChatStore } from '../store.js';
import { MemoryStore } from '../memory.js';
// ... 其余 6 个

export const defaultFactories = {
  'data.messages':      ({ cfg }) => new ChatStore(cfg.store?.maxMessagesPerChat ?? 0),
  'data.memory':        () => new MemoryStore(),
  'data.sessions':      ({ cfg }) => new SessionRegistry(cfg.store?.keepSessionFiles ?? 0),
  'core.send':          (deps) => new SendQueue(deps),
  'data.reminders':     () => new ReminderStore(),
  'core.media':         ({ onebot }) => new VideoReader(onebot),
  'transport':          (deps) => new OneBotClient(deps),
  'core.orchestrator':  (deps) => new Orchestrator(deps),
};

export function createFactories(selected = {}) {
  const table = { ...defaultFactories, ...selected };
  for (const [k, v] of Object.entries(table))
    if (typeof v !== 'function') throw new TypeError(`组件 ${k} 必须是函数`);
  return table;
}

"模块化"的实际价值是四件事：能加层不改源码、能替换单个实现、能整层卸载回滚、能静态预检冲突。这四件事在第 2 档全部具备。

继续往下（换 0.5 的实现）换来的是"代码更干净、少 40% 行数"——但那是给未来维护者省事，不是给现在的功能加分。而代价是丢掉洛版所有实战修复。这笔账在你自己一个人维护的项目里，通常不划算。

03施工顺序

每步结束都必须能正常启动、跑完 31 个单测。任一步失败就地回滚，不要带着问题往下走。

#动作文件验收标准
1备份 app.js，跑一遍基线单测记录通过数—31 个测试文件的基线结果存档
2新建 src/composition/factories.js，8 个工厂全部指向原实现新增文件可 import，无副作用
3把 968–994 的 8 个 new 改成查表app.js单测全绿；启动正常；消息文件字节不变
4给 createApp 加 components 参数（默认空）app.js + 2 处调用方传空对象时行为与第 3 步一致
5加 overrides/ 扫描与 composition.json 解析新增空目录时无变化；坏清单明确报错不静默
6拿 30-desktop-extras 做真实验收拷目录桌宠+壁纸两页出现；删目录重启完全恢复
7（可选）按第 3 档顺序逐个替换实现工厂表每换一个跑一遍单测 + 手工验收
第 6 步是分水岭

如果 30-desktop-extras 能直接跑起来，说明你的容器和 0.5 的层格式真的对齐了——从这一刻起，洛版和 0.5 共用同一套扩展生态，两边写的层可以互相搬。这才是"改造"最大的回报，而不是代码变干净。

如果跑不起来，就停在第 5 步，别再往下走——说明格式还没对齐，硬推第 3 档只会越改越乱。

04三条止损线

① 单测红了不许继续

洛版那 31 个测试文件是唯一的安全网。0.5 的 test/ 没随包，你没有任何外部参照。任何一步让单测变红，先修好再往下——"先记着回头修"在重构里从来没兑现过。

② 第 3 档第 7 步之前，先写清"为什么要换编排器"

如果答案是"为了代码更干净"，别换。如果答案是"洛版的编排逻辑有具体缺陷、我要用 0.5 的某个行为"，那就把那个具体行为列出来，只补那一块，不整体替换。

整体替换 orchestrator 的收益是抽象的，代价是具体的（3,700 行实战逻辑 + 几百条边角修复）。

③ 改造期间冻结功能开发

容器化和业务改动同时进行，冲突会集中在 app.js 那 27 行附近。要么先改完装配层再恢复功能迭代，要么接受每次合入都要重新验证装配。两件事别并行。

05一句话

先搬"装配方式"，别搬"实现"

你要的"模块化底层"，本质是可替换性——加层改行为、单点换实现、整层可卸载。这三件事在第 2 档就全拿到了，代价是 27 行改动 + 一个 60 行的新文件 + 200 行容器逻辑，洛版的行为一行都没丢。

把实现换成 0.5 的，是另一件事：收益是"代码更干净"，代价是"两年踩坑记录清零"。这两件事应该分开决策，不要捆在一起。

真要做第 3 档，就按表里的顺序来，从 data.messages 开始——它格式同源、风险最低，是最合适的第一个实验品。
