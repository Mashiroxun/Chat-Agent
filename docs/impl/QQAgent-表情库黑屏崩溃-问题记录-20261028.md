# 「查看收藏的表情」点击后黑屏 → 自动重启 · 问题记录

- 日期：2026-10-28
- 现象：设置 → 表情系统 → 点「查看收藏的表情」，整个界面变黑，约 1.5 秒后界面重新加载（用户感知为"重启"）
- 结论：**渲染进程原生崩溃（GPU 合成路径），与当天的代码改动无关**；触发条件是表情库面板一次加载 78 张本地图（30MB，含 9 个 1.5–3.7MB GIF）+ 25 张热链

## 一、崩溃事实（日志硬证据）

`G:\QQagent\data\logs\qq-agent-2026-10-28.log`：

```
12:15:09 [ERROR] [window] [渲染进程崩溃] {"reason":"crashed","exitCode":-1073741795}
12:15:40 [ERROR] [window] [渲染进程崩溃] {"reason":"crashed","exitCode":-1073741795}
12:19:53 [ERROR] [window] [渲染进程崩溃] {"reason":"crashed","exitCode":-1073741795}
12:28:24 [ERROR] [window] [渲染进程崩溃] {"reason":"crashed","exitCode":-1073741795}
12:30:31 [ERROR] [window] [渲染进程崩溃] {"reason":"crashed","exitCode":-1073741795}
```

- `-1073741795` = `0xC000001D` = **STATUS_ILLEGAL_INSTRUCTION**（非法指令）。
  这是**原生层**崩溃，不是 JS 异常、不是接口 404、不是 CSP 拦截 —— 后三者在日志里会留下 JS 报错或 `did-fail-load`，本次一条都没有。
- 崩溃转储：`%APPDATA%\qq-agent\Crashpad\reports\` 下 5 个 dmp，时间与上表一一对应（12:15×2 / 12:19 / 12:28 / 12:30），每个约 700KB。
- dmp 里的线程名：`CrRendererMain`、`Compositor`、`GpuMemoryThread`、`Chrome_ChildIOThread` —— 崩溃发生在渲染进程的**合成器/GPU 内存线程**上。

> 旁证：昨天（10-27 17:49）有 8 次 **GPU 进程**崩溃，exitCode `0xC0000005`（访问冲突）。这台机器的显卡/驱动本来就不稳，且有 ToDesk / 向日葵 / EVExtendScreen（远程桌面 + 虚拟显示器）—— 这是 GPU 合成崩溃的典型环境。

## 三、触发条件与放大器

表情库当前数据（`G:\QQagent\data\plugin-data\sticker\`）：

- `storage.json` 59KB，103 条表情
- `img/` 78 个文件、**30MB**，其中 9 个 GIF 单文件 1.5–3.7MB（最大 3.7MB，275×337）
- 另有 25 条热链 `p.qpic.cn`
- 面板 CSS 用了 `backdrop-filter: blur(2px)`（viewer.css:286），强制走 GPU 合成

一次打开 = 78 张本地图解码 + 25 张网络图 + iframe 合成层 + 模糊滤镜。在驱动不稳的机器上，这一组合足以把渲染进程打进 `STATUS_ILLEGAL_INSTRUCTION`。

**放大器**：`openPluginPanel()` 原来没有"已存在就不重复打开"的守卫，连点/双击会叠出多个 overlay + iframe，图片解码内存成倍增长。

## 四、现有兜底的两个缺口

1. **"重启"其实是自动重载，不是重启**
   `electron/main.js:1620` 的 `render-process-gone` 处理：记一条 critical 日志 → 1.5 秒后 `loadURL`。
   用户看到黑屏 1.5 秒再回来，就是这个。
   `rendererCrashCount <= 5` 才重载，**第 6 次起不再重载**，界面会永久停在黑屏，且没有任何提示。

2. **GPU 回退安全网对本次不生效**
   `electron/main.js:97-119` 的 `noteRenderCrash()` 只监听 `child-process-gone` 的 **GPU Process**；
   渲染进程崩溃（本次这种）**不计入** `gpuCrashCount`。
   所以"60 秒内崩 3 次 → 写 `render-gpu-off.flag` → 重启进软件模式"这条自动回退永远不会被触发。
   `render-gpu-off.flag` 至今不存在 → 应用一直在 GPU 模式下跑。

## 五、追加：第一次"关 GPU"为什么没生效（12:36 补）

用户按建议关了 GPU 仍崩 —— 查下来是**关 GPU 的脚本本身坏了**：

```
G:\QQagent\wallpaper-gpu-off.bat
  set "FLAG=%~dp0data\render-gpu-off.flag"
  实际字节：data + 0x0D(CR) + ender-gpu-off.flag
```

源文件里的 `\r` 被当成**回车符**写进了文件，于是 cmd 拿到的路径是
`G:\QQagent\data\<CR>ender-gpu-off.flag` —— 含控制字符的非法文件名，`echo. >` 直接失败，
**flag 从来没被创建过**，应用一直跑在 GPU 模式。

`video-decode-cpu.bat` 同病：`data\render-config.json` → `data<CR>ender-config.json`。

处理：
- 两个 bat 已按字节修正（原文件备份为 `*.bak-20261028`），现在路径是 `data\render-gpu-off.flag` / `data\render-config.json`
- 已直接创建 `G:\QQagent\data\render-gpu-off.flag`（3 字节），**需完全退出应用再启动**才生效

### 对照实验：页面本身没问题

用 Edge（同为 Chromium 内核）无头渲染同一个 URL：

### 崩溃点定位（minidump 解析）

```
ExceptionCode   0xC000001D (STATUS_ILLEGAL_INSTRUCTION)
ExceptionAddress 0x7FF7DB8063B0
Fault in        G:\QQagent\QQ Agent.exe +0x2D263B0
模块列表        42 个，全部是系统 DLL + ffmpeg.dll，**没有任何显卡驱动模块**
```

Electron 33.4.11 / Windows 10.0.26200（25H2）。崩溃在 Electron 主二进制的静态代码段内，

这意味着：关 GPU 只是第一步排除项。若软件模式下仍崩，下一步按以下顺序查：
1. 安全软件 inline hook（本机有火绒）—— 把安装目录加入白名单，或临时退出后重试
2. 某张图片触发的 SIMD 解码路径 —— 把 `img\` 下 9 个 1.5–3.7MB 的 GIF 临时挪走再试
3. Electron 33 在 Win11 25H2 上的兼容性 —— 升级 Electron 版本

### 为什么是"分批"而不是别的

31 个 GIF 的解码内存合计约 **465MB**（最大单张 36MB / 59 帧），加上 47 张静态图与合成层，
一次性全建卡片时峰值很容易顶到渲染进程的承受边界。图片本身没有损坏（Edge 全部能渲染），
所以修的方向是**降低瞬时压力**，而不是"挑出坏图删掉"。

## 八、结论

**这不是代码改动引入的回归**：首次崩溃（12:15:09）早于当天所有写操作；页面本身在 Edge 里能完整渲染 103 张表情；崩溃是 Electron 渲染进程内的原生非法指令（`0xC000001D`，`QQ Agent.exe +0x2D263B0`）。

**也不是 GPU 合成问题**：12:37 那次是在 `render-gpu-off.flag` 生效（软件渲染）之后崩的，时间戳 `12:37:42 启动 → 12:38:02 崩溃`，说明走 CPU 路径一样会崩。

所以定位到的是**渲染压力**：31 个 GIF 合计约 465MB 解码内存 + 103 张卡片的 DOM/合成层，一次性建出来时把渲染进程顶过了界。修复方向因此定为"分批渲染 + 去掉多余的合成层"，而不是继续追 GPU 或驱动。

**对分发的意义**：这类问题在任何装了"几十上百张表情"的机器上都可能复现，跟具体显卡无关。分批渲染是所有用户都受益的改动；GPU 回退、崩溃提示页属于兜底，不能替代它。
